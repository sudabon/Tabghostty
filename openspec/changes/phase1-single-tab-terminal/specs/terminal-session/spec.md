# Spec Delta

## Purpose

Defines the per-session attach, replay, and live lifecycle that keeps each displayed terminal consistent with the daemon's session without injecting stale terminal responses into the shell.

## ADDED Requirements

### Requirement: Attach starts a fresh replay

When the client attaches to a session it SHALL reset that session's terminal state, send an `attach` frame, and enter the replaying phase. `replay` frames SHALL be written to the terminal in order. When a `replay` frame with `done: true` arrives the session SHALL enter the live phase, and the client SHALL send a `resize` frame with the current grid size of the view displaying the session. `output` frames SHALL be written to the terminal in the order received.

#### Scenario: Replay then live

- **WHEN** the client attaches and receives three `replay` chunks, the last with `done: true`, followed by `output`
- **THEN** the terminal shows the replayed content followed by the live output, and a `resize` frame for the view's grid size is sent after the last replay chunk

#### Scenario: Empty ring buffer

- **WHEN** the daemon answers an attach with a single `replay` frame with empty data and `done: true`
- **THEN** the session enters the live phase with an empty terminal

### Requirement: No terminal responses during replay

While a session is replaying, the client SHALL discard every response the terminal engine generates for the PTY (for example DA, DSR, size reports, keyboard-protocol replies) and SHALL NOT send user key input for that session. In the live phase, such responses SHALL be sent to the session as `input` frames.

#### Scenario: Historical query in replay

- **WHEN** replay data contains `ESC[c` (DA1) and `ESC[6n` (DSR)
- **THEN** no `input` frame is sent for that session during the replay

#### Scenario: Same query when live

- **WHEN** the same `ESC[c` arrives in an `output` frame after the session is live
- **THEN** the terminal's DA response is sent to that session as an `input` frame

#### Scenario: Typing during replay

- **WHEN** the user presses keys while the session is replaying
- **THEN** no `input` frame is sent for those keys

### Requirement: Recover from attach overflow

When the client receives an `error` frame with code `attach_overflow` for a session, it SHALL reset that session's terminal and attach again from the beginning.

#### Scenario: Overflow during heavy output

- **WHEN** an `attach_overflow` error arrives for a replaying session
- **THEN** the terminal is reset, a new `attach` is sent, and the screen ends up matching the daemon's buffer without duplicated content

### Requirement: Re-attach after reconnect

After the WebSocket reconnects, the client SHALL re-attach every session it is displaying (resetting each terminal first) and, once live, SHALL send the current grid size. The shell's input line SHALL NOT receive any bytes generated by replaying history.

#### Scenario: Shell input line stays clean

- **WHEN** the daemon is restarted while a shell prompt is displayed, and the client reconnects and replays
- **THEN** the screen is restored and the shell's input line contains no stray characters

### Requirement: Effects handled by other components are ignored

The client SHALL NOT raise desktop notifications from OSC 9, OSC 99, or OSC 777 sequences in the terminal stream, because the daemon parses the same bytes and delivers deduplicated `notify` frames. Terminal title changes SHALL NOT change the tab label. The bell SHALL produce no sound, Dock bounce, or unread mark, matching the current web client.

#### Scenario: OSC 9 in output

- **WHEN** live output contains `ESC]9;done BEL`
- **THEN** the client itself shows no notification for that sequence

#### Scenario: Bell

- **WHEN** live output contains `BEL` outside any OSC sequence
- **THEN** no sound plays and the Dock icon does not bounce
